# Arm MTE

**MTE**（Memory Tagging Extension）は、Armv8.5-Aで導入されたAArch64の機能で、メモリ安全性違反そのものをハードウェアで検出します。「ポインタとメモリの両方にタグを付けてアクセス時に比べる」という考え方はHWASanと同じですが、比較をハードウェアが行うので、オーバーヘッドが小さく本番でも使えます。

CFI、CET、BTI、PACが「メモリ破壊が起きた後の制御の乗っ取り」を防ぐのに対し、**MTEはメモリ破壊そのものを検出するので、data-only attackにも効きます**。

## しくみ

```text
ポインタ:  [63:60 未使用][59:56 タグ][55:0 アドレス]
                          ↑ 論理タグ（ポインタのタグ）

メモリ:    16バイト（granule）ごとに 4ビットの割り当てタグ（allocation tag）
           タグはデータとは別の専用領域に格納される（メモリの約3%）

アクセス時: ポインタのタグ == メモリのタグ ? OK : タグ検査違反
```

ポインタのタグは、TBI（Top Byte Ignore）を利用して最上位バイトの4ビットに入れます。TBIによって最上位バイトはアドレス変換で無視されるので、タグ付きポインタのままロードやストアができます。

タグは4ビットで16種類です。隣接するオブジェクトに違うタグを付けておけば、隣への範囲外アクセスは確実に検出できます。解放時にタグを付け替えておけば、use-after-freeも、タグが偶然一致する場合（1/16程度）を除いて検出できます。

### 主な命令

| 命令 | 動作 |
|---|---|
| `IRG Xd, Xn` | Xnにランダムなタグを付けた値をXdに入れる（除外するタグを指定可能） |
| `ADDG`、`SUBG` | アドレスとタグを同時に加減算する |
| `STG`、`ST2G` | 1つ／2つのgranuleにタグを設定する |
| `STZG`、`STZ2G` | タグを設定し、同時にゼロクリアする |
| `STGP` | 2つのレジスタの値をストアし、同時にタグを設定する |
| `LDG` | メモリのタグを読んでポインタに入れる |
| `DC GVA`、`DC GZVA` | キャッシュラインサイズのブロック全体にタグを設定する（Zはゼロクリアも） |
| `MSR TCO, #1` | タグ検査を一時的に無効にする（Tag Check Override） |

### 検査のモード

| モード | 違反の報告 | 精度 | オーバーヘッド | 用途 |
|---|---|---|---|---|
| 同期（sync） | 違反した命令でただちに例外 | 正確 | 大きめ | デバッグ、セキュリティ重視の本番 |
| 非同期（async） | 後でまとめて通知 | 違反があったことだけわかる | 小さい | 本番 |
| 非対称（asymm） | 読み込みは同期、書き込みは非同期 | 中間 | 中間 | 本番（FEAT_MTE3が必要） |

Linuxでは、同期モードの違反は`SIGSEGV`（`si_code`は`SEGV_MTESERR`）、非同期モードの違反は`SIGSEGV`（`SEGV_MTEAERR`）で通知されます。

## 使い方

### Linuxのユーザー空間

Linux 5.10以降で、ユーザー空間からMTEを使えます。`prctl(PR_SET_TAGGED_ADDR_CTRL, ...)`でタグ付きアドレスの利用と検査のモードを設定すると、`PROT_MTE`付きで`mmap`した領域がタグ検査の対象になります。タグの設定は`IRG`や`STG`でユーザー空間から直接行います。

次のプログラムは、32バイトのオブジェクトにタグを付け、その直後に書き込むとフォールトすることを確かめるものです。

```c
#include <arm_acle.h>
#include <stdio.h>
#include <stdint.h>
#include <sys/mman.h>
#include <sys/prctl.h>

#ifndef PROT_MTE
#define PROT_MTE 0x20
#endif

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    /* タグ付きアドレスを許可し、同期モードでタグ検査を有効にする。
       IRG が生成してよいタグの集合として、0 以外（0xfffe）を指定する */
    if (prctl(PR_SET_TAGGED_ADDR_CTRL,
              PR_TAGGED_ADDR_ENABLE | PR_MTE_TCF_SYNC | (0xfffe << PR_MTE_TAG_SHIFT),
              0, 0, 0) != 0) {
        perror("prctl");
        return 1;
    }
    /* PROT_MTE 付きでメモリを確保する（初期状態のタグはすべて 0） */
    unsigned char *page = mmap(NULL, 4096, PROT_READ | PROT_WRITE | PROT_MTE,
                               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (page == MAP_FAILED) { perror("mmap"); return 1; }

    /* 32バイト(2グラニュール)のオブジェクトにランダムなタグを付ける */
    unsigned char *obj = __arm_mte_create_random_tag(page, 0);  /* IRG */
    __arm_mte_set_tag(obj);                                     /* STG */
    __arm_mte_set_tag(obj + 16);
    printf("page=%p obj=%p\n", (void *)page, (void *)obj);

    obj[31] = 1;          /* OK: タグが一致する */
    printf("in-bounds write ok\n");
    obj[32] = 1;          /* NG: 次のグラニュールはタグ0のまま → SIGSEGV (SEGV_MTESERR) */
    printf("not reached\n");
    return 0;
}
```

MTE対応のハードウェアがなくても、QEMUのユーザーモードエミュレーションで試せます。

```text
$ aarch64-linux-gnu-gcc -O1 -march=armv8.5-a+memtag -static -o mte mte.c
$ qemu-aarch64 -cpu max ./mte
page=0x400000812000 obj=0x600400000812000     ← 最上位バイトにタグ 6 が付いている
in-bounds write ok
qemu: uncaught target signal 11 (Segmentation fault) - core dumped
```

### アロケータとコンパイラの対応

glibc 2.33以降の`malloc`は、チューナブル`glibc.mem.tagging`でMTEを有効にできます。Androidの標準アロケータであるScudoもMTEに対応しています。Clangは、スタック変数にタグを付ける`-fsanitize=memtag-stack`や、`-fsanitize=memtag-heap`、`-fsanitize=memtag-globals`を提供しています（主にAndroid向け）。Linuxカーネル自身も、KASANのHW_TAGSモードでMTEを使えます。

### プラットフォームの状況

AndroidはOSとScudoが早くからMTEに対応しています。Pixel 8がMTE対応ハードウェアを搭載した最初の端末で、開発者オプションから有効にできます。アプリケーションはマニフェストの`android:memtagMode`で`sync`か`async`を指定できます。

Appleは2025年に、A19などのチップでMTEを強化したEMTE（Enhanced MTE）を使う、Memory Integrity Enforcementを発表しました。カーネルと多くのプロセスで同期モードのタグ検査を常時有効にしているとされます。

## コード生成器が気を付けること

自分の言語がMTEの恩恵を受ける典型的な形は、ランタイムのアロケータがタグを付けることです。タグ付きポインタでそのままロードやストアをすればハードウェアが検査してくれるので、コード生成器の側で特別なことはほとんどいりません。

ただし、ポインタの最上位バイトを壊すコードを生成してはいけません。ポインタを`0x00ffffffffffffff`でマスクしたり、上位ビットにフラグを入れたりすると、タグが消えます。「ヒープの範囲内か」の判定や異なるオブジェクト間の差分では、タグを取り除いてから計算します。

スタック上のオブジェクトにタグを付けるなら、関数の入口でタグを付けて出口でタグ0に戻すコードを生成し、オブジェクトを16バイト境界にそろえて配置します。

## ランタイム・FFIで気を付けること

### 独自アロケータとGCヒープ

**ランタイムが独自のアロケータやGCヒープを持つ場合、MTEの恩恵を受けるにはアロケータ自身がタグを付ける必要があります**。

1. ヒープ領域を`PROT_MTE`付きで`mmap`します。
2. 割り当て時に`IRG`でランダムなタグを選び（除外マスクで隣と違うタグにする）、オブジェクトのgranuleに`STG`や`ST2G`でタグを設定します。サイズは16バイト単位に切り上げます。
3. 解放時に別のタグへ付け替えます。これでuse-after-freeが検出されます。

GCヒープなら、割り当て時のゼロクリアとタグの設定を`STZG`や`DC GZVA`で同時に済ませられます。移動型GCでは、移動先で新しいタグを付け、参照側のポインタのタグも書き換えます。

### ポインタの上位ビットを使ったタグ付け

動的型付き言語のランタイムがよく使うタグ付きポインタのうち、**上位ビットを使う方式はMTEと衝突します**。

| 方式 | MTEとの関係 |
|---|---|
| 下位ビットを使う | 問題なし |
| NaN-boxing（上位16ビットを使う） | ポインタを取り出すときに上位ビットを0にすると、タグが消える |
| 最上位バイトに独自のタグを入れる | MTEのタグと直接衝突する |
| 圧縮ポインタ（ベースからのオフセット） | 復元するときにタグが消える |

下位ビットのタグ付けに切り替えるか、NaN-boxingなどでMTEのタグ（ビット56〜59）を保存できる場所を確保して取り出すときに戻すか、MTEを使う領域（Cのヒープ）と言語のヒープを分けて言語のヒープではMTEを使わないか、のいずれかで対処します。

この問題はMTEが無効でも起こりえます。Android 11以降の64ビットプロセスでは、MTE非対応のハードウェアでも、`malloc`が返すポインタの最上位バイトに常に非ゼロの値が入っています（TBIを利用した「Tagged Pointers」機能）。上位ビットが0だと仮定して自分の用途に使っていたアプリケーションやランタイムは、これでクラッシュするようになりました。**ポインタの上位ビットが0だと仮定してはいけません**。

### 保守的GCとメモリの総なめ

保守的GCや、複数のオブジェクトにまたがるメモリコピー、ヒープのダンプは、どのタグのメモリも同じポインタで読むので、タグ検査違反になります。`MSR TCO, #1`でタグ検査を一時的に無効にする（終わったら必ず戻す）か、`LDG`で正しいタグを読んでからアクセスします。保守的GCで「ポインタらしき値」がヒープを指しているかを判定するときは、値からタグを取り除いてからヒープの範囲と比べます。

### システムコールとFFI

タグ付きポインタをシステムコールに渡すには、`PR_TAGGED_ADDR_ENABLE`によるタグ付きアドレスABIの有効化が必要です。Goのようにlibcを経由せずシステムコールを発行するランタイムは注意しましょう。

Cのライブラリが返すポインタはタグ付きかもしれないので、保存や比較のときに上位ビットを落としてはいけません。逆に、自分のランタイムがMTE有効のプロセスにロードされる場合も考えておきます（Androidアプリケーションのネイティブライブラリなど）。ランタイムが`mmap`したメモリは検査されませんが、Cの`malloc`から得たメモリは検査の対象です。

### スタックのタグ付けと非局所脱出

スタック変数にタグを付けている場合、関数の出口を通らずにフレームを捨てると、捨てたフレームのタグが残り、後で誤検知を起こします。Androidのbionicは`longjmp`のときにスタックのタグをクリアしています。独自の非局所脱出を持つ処理系も同じく、捨てたスタック領域のタグを0に戻す必要があります。スタックをコピーする実装ではタグもコピーします。

### コードポインタにはタグを付けない

TBIはデータアクセスにだけ適用され、命令アドレスには適用されません（Linuxでは命令アドレスの上位ビットはPACに使われます）。関数ポインタやリターンアドレスにMTEのタグを付けてはいけません。

## 限界

- ランダムなタグによる検出は確率的です。ただし隣接オブジェクトのタグを必ず変えれば、隣への範囲外アクセスは確実に検出できます。
- 16バイトのgranule内でのはみ出し（10バイトのオブジェクトの11バイト目など）や、構造体の中のフィールドからのはみ出しは検出できません。
- 投機的実行でタグを推測する攻撃（2024年のTikTagなど）が報告されています。
