# Control Flow Integrity

**Control Flow Integrity**（CFI）は、実行時の制御フローがコンパイル時に決まる制御フローグラフからはみ出さないことを保証しようとする考え方です。2005年にAbadiらが提案しました。

完全なCFIは難しいので、実際の実装は「間接分岐の飛び先として許される集合」を何らかの形で近似し、そこから外れた分岐を止めます。近似が細かいほど保護は強くなりますが、コストや互換性の問題も大きくなります。本章ではソフトウェアによる実装を見て、次の章からハードウェアによる実装に進みます。

## 精度による分類

| 精度 | 許可される飛び先 | 実装例 |
|---|---|---|
| 粗い | 間接分岐の飛び先になりうる場所すべて | Intel CET IBT、Arm BTI、Windows CFG |
| 中程度 | シグネチャが一致する関数 | Clang CFI（`cfi-icall`）、kCFI、FineIBT |
| 細かい | クラス階層にもとづくvtableなど | Clang CFI（`cfi-vcall`） |

粗いCFIでも、関数の途中や任意の命令境界へは飛べなくなるので、使えるガジェットは大幅に減ります。

## Clang CFI

Clangの`-fsanitize=cfi`は、LTOでプログラム全体を見て、型ごとに許される飛び先の集合を計算します。

```sh
clang -flto -fvisibility=hidden -fsanitize=cfi foo.c bar.c
```

| スキーム | 検査内容 |
|---|---|
| `cfi-icall` | 間接関数呼び出しの飛び先が、関数ポインタと同じ型の関数か |
| `cfi-vcall`、`cfi-nvcall` | 仮想関数呼び出しのvtableが、静的な型のクラス階層に属するか |
| `cfi-derived-cast`、`cfi-unrelated-cast` | `static_cast`などのキャストが正しいか |
| `cfi-mfcall` | メンバー関数ポインタ経由の呼び出し |

実装にはジャンプテーブルを使います。アドレスを取られた関数を型ごとにまとめ、関数ポインタの値をジャンプテーブルのエントリのアドレスに置き換えます。呼び出し時の検査は「その型のテーブルの範囲内で、エントリ境界にそろっているか」だけなので高速です。

その代わり、LTOが必須で、共有ライブラリをまたぐには`-fsanitize-cfi-cross-dso`がいります。また、関数ポインタの値が関数本体のアドレスと一致しなくなるので、関数ポインタとシンボルのアドレスを比較するコードは壊れます。

Clang CFIが実際に出力するチェックのコードや、`-fsanitize-cfi-cross-dso`での動作は、『Binary Hacks Rebooted』のHack #58でgdbを使って追いかけています。

## kCFI

**kCFI**（`-fsanitize=kcfi`）は、Linuxカーネル向けに作られた、LTO不要の型ベースのCFIです。各関数の直前に型のハッシュ値を埋め込み、間接呼び出しの直前に照合します。

```c
int call(int (*fp)(int), int x) { return fp(x); }
int target(int x) { return x + 1; }
```

AArch64向けにコンパイルすると次のようになります。

```asm
    .word   1631892647              // call 自身の型ハッシュ（int (*)(int (*)(int), int)）
call:
    mov     x2, x0
    mov     w0, w1
    ldur    w16, [x2, #-4]          // 飛び先の直前4バイト = 飛び先の型ハッシュ
    movk    w17, #1940
    movk    w17, #5, lsl #16        // 期待するハッシュ 0x50794（int (*)(int)）
    cmp     w16, w17
    b.eq    .Ltmp0
    brk     #0x8222                 // 不一致ならトラップ
.Ltmp0:
    br      x2

    .word   329620                  // 0x50794: target の型ハッシュ
target:
    add     w0, w0, #1
    ret
```

ハッシュ値は、関数の型をItanium C++ ABIの方式でマングリングした文字列から計算します。別々にコンパイルされたオブジェクトでも型が同じならハッシュが一致するので、LTOがなくても、共有ライブラリをまたいでも動きます。x86-64には、ハッシュの照合を呼び出される側に移してIntel CETのIBTと組み合わせたFineIBTもあります（Linuxカーネル6.2以降）。

### 型ハッシュの互換性

**kCFIで保護されたCのコードが、自分の言語の関数をコールバックとして呼ぶとき、Cの型として同じハッシュ値が関数の直前に置かれていなければトラップします**。kCFIを使う環境（Linuxのカーネルモジュールなど）と相互運用したい処理系は、FFIで公開する関数のCでの型を決め、Itanium ABIの規則でマングリングし、同じハッシュ関数で求めた値を関数の直前に置く必要があります。

Rustは`-Zsanitizer=kcfi`と`-Zsanitizer=cfi`でこれに対応しています。やっかいなのは、Rustの`i32`とCの`int`のように、表現は同じでも型名が違うケースです。そこで、整数型を型名ではなくビット幅で表す正規化オプション（Clangの`-fsanitize-cfi-icall-experimental-normalize-integers`、Rustの`-Zsanitizer-cfi-normalize-integers`）が用意されています。言語をまたいでCFIを使うなら、正規化の有無を双方でそろえます。

## Windows Control Flow Guard（CFG）

Windowsの**CFG**（`/guard:cf`）は、粗いforward edgeのCFIです。コンパイラがアドレスを取られる関数の一覧を出力して間接呼び出しをチェック関数経由にし、リンカが有効な飛び先の一覧を実行ファイルに埋め込みます。ローダはそれを16バイト単位のビットマップにし、チェック関数はこのビットマップを引きます。

自前のコード生成器でCFGに参加するには、COFFの`.gfids$y`セクションにアドレスを取られる関数の一覧を出力し、間接呼び出しを`__guard_check_icall_fptr`などのチェック関数経由にします。LLVMなら`cfguard`モジュールフラグを設定するだけで済みます。JITで生成した関数は、`SetProcessValidCallTargets()`で有効な飛び先として登録します。

型のハッシュを使う後継のXFG（eXtended Flow Guard）も開発されましたが、広くは使われていません。

## backward edgeのソフトウェア保護

### ShadowCallStack

Clangの`-fsanitize=shadow-call-stack`は、リターンアドレスを別のスタックにも保存し、戻るときはそちらを使います。AArch64では、shadow call stackのポインタをx18レジスタに置きます。

```asm
f:
    str  x30, [x18], #8      // リターンアドレスをシャドウに積む
    ...
    ldr  x30, [x18, #-8]!    // シャドウから取り出す
    ret
```

処理系開発者にとって大事なのはx18の扱いです。AArch64のABIでx18はプラットフォームレジスタとされ、用途はプラットフォームが決めます。

| プラットフォーム | x18の扱い |
|---|---|
| Apple（macOS、iOS） | 予約。ユーザーコードは使用禁止 |
| Windows | 予約（TEBを指す） |
| Android | ShadowCallStackのために予約 |
| Linux（一般） | 一時レジスタとして使用可能 |

**自前のコード生成器がx18をレジスタ割り当てに使っていると、これらのプラットフォームでは壊れます**。Linuxでも、ShadowCallStackを使うライブラリとリンクする可能性があるなら避けるのが無難です。

### SafeStack

Clangの`-fsanitize=safe-stack`は、スタックを2本に分けます。リターンアドレスやアドレスを取られない変数は安全なスタックに、配列やアドレスを取られる変数は安全でないスタックに置き、範囲外書き込みがリターンアドレスに届かないようにします。スタックが2本あるので、スタックを切り替えたりスキャンしたりするランタイムとは相性がよくありません。

## 安全な言語とCFI

メモリ安全な言語のコードは、関数ポインタやリターンアドレスを不正に書き換えられないはずなので、言語自身のコードにCFIを入れる必要性は低めです。CFIが効いてくるのは、ランタイムがC/C++で書かれているとき、FFI先のCがコールバックのテーブルやクロージャの環境を壊しうるとき、`unsafe`なコードがあるとき、JITのバグで生成コードが安全性を破るときです。

そしてもう1つ、**周囲のCがCFIを使っている環境では、言語側が協調しないとそもそも動かない**という相互運用の問題があります。
