# 脅威モデルと緩和策の全体像

hardening機構は、それぞれ攻撃の流れの特定の段階を止めるように作られています。どの段階を止めるものかがわかると、各機構の限界も見えてきます。

## メモリ安全性違反

ネイティブコードの脆弱性の大部分は、**メモリ安全性違反**から始まります。MicrosoftやGoogle（Chromium、Android）は、深刻な脆弱性のおよそ7割がメモリ安全性の問題だと繰り返し報告しています。

| 種類 | 内容 | 例 |
|---|---|---|
| 空間的違反（spatial） | オブジェクトの範囲外にアクセスする | バッファオーバーフロー、type confusionによる範囲外アクセス |
| 時間的違反（temporal） | 寿命が尽きたオブジェクトにアクセスする | use-after-free、double free、use-after-return |

このほか、未初期化メモリの読み出しとデータ競合も、安全性を損なう代表的なバグです。

## 攻撃の流れと緩和策

典型的な攻撃は次のように進みます。

```text
 (1) バグを踏む       → 範囲外書き込み、UAF など
 (2) 足場を作る       → 任意アドレス読み出し / 書き込みの能力（primitive）を得る
 (3) 制御を奪う       → リターンアドレス・関数ポインタ・vtable を書き換える
 (4) 目的を達成する   → 任意コード実行、権限昇格、情報窃取
```

| 段階 | 緩和策の方向性 | 代表例 |
|---|---|---|
| （1） | メモリ安全性違反そのものを検出する | サニタイザ、MTE、CHERI、境界検査 |
| （2） | アドレスを推測しにくくし、書き換え先を減らす | ASLR、RELRO |
| （3） | 制御フローの整合性を守る | スタックカナリア、CFI、CET、BTI、PAC |
| （4） | できることを減らす | NX、W^X、サンドボックス、seccomp |

この資料で扱う命令セット拡張は、主に（1）と（3）を担当します。

## 制御フローの乗っ取り

NXが当たり前になった今、攻撃者は自分で書いた機械語を直接は実行できません。そこで、すでにメモリ上にあるコードの断片（ガジェット）をつなぎ合わせます。リターンアドレスを書き換えて`ret`で終わるガジェットをつなぐのが**ROP**（Return-Oriented Programming）、関数ポインタやvtableを書き換えて間接`jmp`／`call`で終わるガジェットをつなぐのがJOP／COPです。

これに対応して、制御フローの保護は2方向に分けて考えます。

```text
            forward edge（前向きの辺）
  caller ──── 間接call / 間接jmp ────▶ callee
         ◀─── ret ─────────────────
            backward edge（後ろ向きの辺）
```

| 保護対象 | 攻撃 | ソフトウェアによる対策 | ハードウェアによる対策 |
|---|---|---|---|
| backward edge（`ret`） | ROP | スタックカナリア、ShadowCallStack、SafeStack | CET Shadow Stack、Arm GCS、Arm PAC（pac-ret）、RISC-V Zicfiss |
| forward edge（間接call／jmp） | JOP、COP | Clang CFI、kCFI、Windows CFG | CET IBT、Arm BTI、Arm PAC（関数ポインタの署名）、RISC-V Zicfilp |

ハードウェアによるforward edgeの保護（IBT、BTI）は、「間接分岐の飛び先は特定の命令で始まらなければならない」という粗い制約です。関数の型までは見ないので、`free`の代わりに`system`を呼ばせるような「別の関数の先頭」への差し替えは防げません。型を見るソフトウェアCFIと組み合わせる意味はここにあります。

## データ専用攻撃

制御フローを守っても終わりではありません。**データ専用攻撃**（data-only attack）は、制御フローを一切乱さずに、権限フラグやファイル名などを書き換えて目的を果たします。CFI系の機構はこれを防げないので、根本的には段階（1）でメモリ安全性違反そのものを止める必要があります。MTEやCHERIが注目されているのはこのためです。

## 検出用と本番用

| | 開発・テスト用 | 本番用 |
|---|---|---|
| 目的 | バグを見つける | 攻撃を止める |
| オーバーヘッド | 数倍まで許容 | 数%以下が望ましい |
| 誤検知 | ある程度許容 | 許されない |
| 例 | ASan、MSan、TSan、UBSan | CET、BTI、PAC、MTE（非同期モード）、CFI、スタックカナリア |

MTEは同期モードならデバッグに、非同期モードなら本番に使えるので、両方の性質を持っています。

## 処理系開発者の3つの立場

はじめにで述べた3つの立場を、機構ごとに整理しておきます。以降の章では、この表の各マスを詳しく見ていきます。

| 機構 | 処理系が提供するもの | 処理系の実装が壊しうるもの |
|---|---|---|
| NX、W^X | なし | JIT、トランポリン |
| スタックカナリア | 関数のプロローグとエピローグ | なし |
| サニタイザ | メモリアクセスの計装 | 独自アロケータ、スタック切り替え、GCのスキャン |
| CET IBT、BTI | 間接分岐先のlanding pad、ELFプロパティ | 手書きアセンブリ、JIT、計算型goto |
| Shadow Stack、GCS | ELFプロパティ | スタック切り替え、独自アンワインダ、リターンアドレスの書き換え |
| PAC | プロローグでの署名、エピローグでの検証 | スタックのコピー、リターンアドレスの読み取り |
| MTE | スタックへのタグ付けなど | 独自アロケータ、ポインタのタグ付け、保守的GC |
