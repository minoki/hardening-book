## ELFプロパティとリンク

**最もありがちで、最も気付きにくい問題です**。

Intel CET、Arm BTI、Arm GCSは、オブジェクトファイルの`.note.gnu.property`で対応を宣言し、リンカは全入力の論理積を出力に設定します。処理系が出力するオブジェクト、ランタイムの手書きアセンブリ、FFI先のCライブラリ、ディストリビューションのスタートアップファイルのどれか1つでもプロパティを欠いていれば、出力されたバイナリでは保護が黙って無効になります。

対策は次の通りです。

1. コード生成器が出力するすべてのオブジェクトに正しいプロパティを付けます。付けてよいのは、中身が本当に対応しているとき（landing padが正しく置かれ、リターンアドレスを不正に扱っていないとき）だけです。
2. ランタイムのCコードは`-fcf-protection=full`（x86-64）や`-mbranch-protection=standard`（AArch64）でビルドします。
3. ランタイムのアセンブリには手でプロパティを書きます（Arm BTIの章に例があります）。
4. CIで`-z cet-report=error`や`-z bti-report=error`を付けてリンクし、最終成果物を`readelf -n`で確認します。

```sh
# CI でのチェック例
readelf -n ./mylang-program | grep -E 'x86 feature: .*IBT.*SHSTK|AArch64 feature: .*BTI' \
  || { echo "hardening properties missing"; exit 1; }
```

## Cからのコールバックとクロージャ

処理系が生成した関数をCに渡す場面（コールバック、`qsort`の比較関数、`pthread_create`のエントリ、シグナルハンドラなど）では、次の対応がいります。

| 機構 | 必要な対応 |
|---|---|
| IBT、BTI | 関数の先頭に`ENDBR64`か`BTI c`（または`PACIASP`） |
| kCFI、Clang CFI | Cの型として同じ型ハッシュを置く（[CFIの章](./cfi.md#型ハッシュの互換性)） |
| arm64e | IA鍵、modifier 0で署名してから渡す |
| Windows CFG | アドレスを取られる関数として登録する |

環境ポインタを渡す引数のないAPIに、クロージャを関数ポインタ1つで渡したいなら、トランポリンを実行時に用意することになります。スタック上には作らず、W^Xを守り、先頭に`ENDBR64`や`BTI c`を置き（BTIならページを`PROT_BTI`にし）、arm64eでは署名してから渡します。libffiのclosure APIはこうしたプラットフォームの違いを吸収してくれるので、自前で実装する前に検討する価値があります。libffiの使い方は『Binary Hacks Rebooted』のHack #84に、実行時に機械語を生成して関数を部分適用する例はHack #85にあります。

## スタック切り替え

コルーチン、グリーンスレッド、ファイバー、エフェクトハンドラでスタックを切り替えるときに必要な対応です。

| 機構 | 必要な対応 |
|---|---|
| ASan | `__sanitizer_start_switch_fiber`と`__sanitizer_finish_switch_fiber`で切り替えを通知する |
| TSan | `__tsan_create_fiber`、`__tsan_switch_to_fiber`、`__tsan_destroy_fiber`を使う |
| CET Shadow Stack | コルーチンごとに`map_shadow_stack`で確保し、`RSTORSSP`と`SAVEPREVSSP`で切り替える |
| Arm GCS | コルーチンごとに確保し、`GCSSS1`と`GCSSS2`で切り替える |
| PAC | 同じスタックに戻る限り問題ない。新しいコルーチンへの最初の遷移では`autiasp`を通らないようにする |
| MTE（スタックのタグ付け） | スタックを`PROT_MTE`付きで確保し、破棄や再利用のときにタグをクリアする |

新しいコルーチンを、偽のスタックフレームに`ret`することで開始する方法は避けましょう。Shadow StackやGCSには戻り先が積まれておらず、PACの署名もないので、どの保護でも失敗します。エントリ関数には`br`や`jmp`で入り、エントリ関数からは戻らない（戻ったら専用の後始末に行く）ようにします。

**コンテキスト切り替えのコードはランタイムの1ヵ所に集約し、すべての機構への対応をそこにまとめるのがよい設計です**。`ucontext.h`でコルーチンを実装する例は『Binary Hacks Rebooted』のHack #80にあります。glibcの`swapcontext`はShadow Stackに対応済みなので、まずはこれで試すのが手軽です。

## 非局所脱出

例外、`longjmp`、エフェクトハンドラからの脱出、継続の呼び出しなど、関数の出口を通らずにフレームを捨てるときに必要な対応です。

| 機構 | 必要な対応 |
|---|---|
| ASan | 独自の機構なら、脱出前に`__asan_handle_no_return()`を呼ぶ |
| IBT、BTI | 間接ジャンプで飛ぶランディングパッドに`ENDBR64`か`BTI j`を置く |
| CET Shadow Stack | 捨てたフレームのぶんだけ`INCSSPQ`で巻き戻す |
| Arm GCS | `GCSPOPM`で同様に巻き戻す |
| PAC | 独自のアンワインダでは保存されたLRのPACを取り除く。脱出先へは`br`で飛ぶ |
| MTE（スタックのタグ付け） | 捨てたスタック領域のタグをクリアする |

C++の例外やCの`longjmp`を使うなら、これらはライブラリが済ませてくれます。独自のアンワインダを実装するなら、glibcの`__longjmp.S`（`sysdeps/x86_64`や`sysdeps/aarch64`）がShadow StackやGCSにどう対応しているかが参考になります。脱出先で保存しておいたShadow Stackのポインタまで巻き戻すのが一番簡単です。

## スタックのコピーと移動

スタックの内容をコピーする実装（first-class continuation、スタックの拡張、スナップショット）は、**Shadow StackやGCSとは基本的に両立せず、PACとは再署名が必要になります**。Shadow StackとGCSは普通の命令では書き戻せず、pac-retの署名はSPに、ASanのポイズンとMTEのタグはアドレスに結び付いているからです。

新しく処理系を設計するなら、継続をワンショットに制限してスタック切り替えで実装する、セグメント化スタックで伸ばす（性能上の問題は知られています）、スタックごとに十分な仮想アドレス空間を予約して物理メモリだけ必要に応じて割り当てる、といった、スタックを移動しない設計を選ぶのが無難です。

## GC

### スタックスキャン

- PAC：保存されたリターンアドレスは署名済みです。スタックマップを引く前に`XPACI`や`XPACLRI`でPACを取り除きます。
- ASan：`detect_stack_use_after_return`が有効ならローカル変数はfake stackにあるので、そちらもスキャンするかオプションを切ります。スキャン関数は`no_sanitize("address")`にします。
- MTE：スタックにタグを付けているなら、TCOでタグ検査を無効にしてから読みます。
- Shadow Stack、GCS：リターンアドレスしかないのでスキャン対象ではありません。逆に、改ざんされていない信頼できるリターンアドレスの列として、フレームをたどるのに使うこともできます。

### スレッドの停止

セーフポイントでスレッドを止めるためのreturn address hijackingは、Shadow Stack、GCS、PACと衝突します。フラグの確認やガードページへのアクセスによるポーリングに切り替えるのが確実です。

### ヒープスキャン

保守的GCやヒープの総なめでは、ASanのためにスキャン関数を計装から外し、MTEのためにTCOで検査を無効にします。「ポインタらしき値」の判定では、MTE、HWASan、AndroidのTagged Pointersのタグを取り除いてからヒープの範囲と比べます。

## 独自アロケータ

**ランタイムが`malloc`の上に独自のアロケータを持つと、サニタイザやMTEはその中のバグを見つけられません**。

| 機構 | 対応 |
|---|---|
| ASan | 未割り当てと解放済みの領域をポイズンし、オブジェクト間にレッドゾーンを空け、解放したメモリをすぐ再利用しない |
| MSan | 新しく割り当てたメモリを`__msan_allocated_memory`で未初期化としてマークする |
| LSan | ランタイムのヒープを`__lsan_register_root_region`でルートとして登録する |
| MTE | ヒープを`PROT_MTE`で確保し、割り当て時にタグを付け、解放時に付け替える |
| HWASan | `__hwasan_tag_memory`などでタグを付ける |

デバッグビルドだけでも大きな効果があります。ランタイム内部のアロケータはユーザーのコードから見えないので、ここにバグがあると発見が非常に困難です。テスト用に、独自アロケータを無効にして全割り当てを`malloc`に回すモードを用意しておくのも有効です。注釈なしでASanなどの恩恵を受けられます。

## タグ付きポインタ

ポインタに型情報などを埋め込むなら、アライメントで空いている下位ビットを使うのが最も安全です。NaN-boxingや最上位バイトのタグのように上位ビットを使うと、MTE、HWASan、AndroidのTagged Pointers、arm64eのPACと衝突しえます。

ポインタの上位ビットが0だと仮定してはいけません。取り出すときは上位ビットを0で埋めず、元の値に戻します。上位16ビットを保存できないNaN-boxingでは、MTEを使うヒープのポインタを格納できないことになります。NaN-boxingそのものについては『Binary Hacks Rebooted』のHack #79を参照してください。

## JIT

JITを持つ処理系では、ここまでのすべてが生成コードに関わります。

| 項目 | 対応 |
|---|---|
| W^X | `mprotect`の切り替え、二重マッピング、`MAP_JIT`（Apple）、メモリ保護キーのいずれかを使う |
| IBT | 生成コードの間接分岐の飛び先に`ENDBR64`を置く（ユーザー空間のIBTが有効になる日に備える） |
| BTI | 生成コードのページを`PROT_BTI`で確保し、飛び先に`BTI`命令を置く |
| PAC（pac-ret） | 生成コードも同じプロローグとエピローグの規則に従う |
| PAC（arm64e） | Cから呼ぶエントリは署名してから渡し、Cの関数ポインタは検証してから呼ぶ |
| Shadow Stack、GCS | `call`と`ret`が対になっていれば対応不要 |
| CFG（Windows） | `SetProcessValidCallTargets`で飛び先を登録する |
| キャッシュ | AArch64では、書き込み後に命令キャッシュをフラッシュする（`__builtin___clear_cache`） |
| アンワインド情報 | `__register_frame`などで登録する。pac-retを使うなら`DW_CFA_AARCH64_negate_ra_state`も含める |

**JITコードは攻撃者がある程度内容をコントロールできるので、特にBTIやIBTで守るべき場所です**。

## インタプリタのディスパッチ

| 方式 | IBT、BTIで必要な対応 |
|---|---|
| `switch`文 | コンパイラがジャンプテーブルに`notrack`（x86）や`BTI j`（AArch64）を付けるので、何もしなくてよい |
| 計算型goto（direct threading） | ハンドラのラベルに`ENDBR64`か`BTI j`が必要。GCCとClangは自動で付ける |
| アセンブリで書いたインタプリタ | ハンドラの先頭に手で`ENDBR64`か`BTI j`を書き、ELFプロパティも付ける |
| 末尾呼び出しによるディスパッチ | AArch64では`br x16`か`br x17`を使えば、ハンドラは`BTI c`で受けられる |
| subroutine threading | 通常の関数呼び出しなので、特別な対応は不要 |

## レジスタの予約

| アーキテクチャ | レジスタ | 理由 |
|---|---|---|
| AArch64 | x18 | AppleとWindowsでは予約、AndroidではShadowCallStackが使う |
| AArch64 | x16、x17 | リンカのveneerやPLTが壊す。BTIでは間接末尾呼び出しに使う |
| AArch64 | x30（LR） | pac-retを使うなら、署名済みかどうかを常に追跡する |
| x86-64 | なし | CETは汎用レジスタを予約しない |

## シグナルハンドラ

シグナルハンドラは関数として呼ばれるので、BTIでは`BTI c`（または`PACIASP`）が必要です。

Shadow Stackが有効なら、カーネルはシグナルフレームの情報をShadow Stackにも積み、`sigreturn`で検証します。シグナルハンドラの中で`ucontext`のPCやスタックポインタを書き換えて別の場所に戻る手法（JITのコードパッチ、GCのセーフポイント、ゼロ除算の例外への変換など）を使うなら、Shadow Stackとの整合に注意が必要です。

代替シグナルスタック（`sigaltstack`）はASanの計装の対象外なので、そこで動くコードの誤検知や見逃しにも気を付けましょう。

## テスト戦略のまとめ

| 目的 | 方法 |
|---|---|
| ランタイムのメモリバグを見つける | ランタイムをASanとUBSan付きでビルドしたテストをCIで回す。独自アロケータには注釈を入れる |
| データ競合を見つける | ランタイムをTSan付きでビルドしたテストを回す |
| FFI境界のバグを見つける | FFIのテストをASan付きで回す。可能なら自分の言語のコードにもASanの計装を入れる |
| ハードウェア機構への対応を確かめる | `readelf -n`でELFプロパティを確認する。QEMU（`-cpu max`）でBTI、PAC、MTEを、Intel SDEでCETを有効にしてテストを回す |
| 実機で確かめる | `GLIBC_TUNABLES=glibc.cpu.hwcaps=SHSTK`でShadow Stackを有効にしてテストを回す |
| 広くバグを探す | ランタイム、パーサ、FFI境界をファジングする |
