# はじめに

この資料は、プログラミング言語処理系、特にネイティブコードを生成する処理系を作る人に向けて、プログラムの安全性を高めるしくみ（hardening）をまとめたものです。中心となるのは、次のようなCPUの命令セット拡張です。

- Intel CET（Indirect Branch TrackingとShadow Stack）
- Arm BTI（Branch Target Identification）
- Arm Pointer Authentication（PAC）
- Arm MTE（Memory Tagging Extension）

合わせて、ソフトウェアによる対策であるサニタイザ（ASan、MSanなど）とControl Flow Integrity（CFI）、そのほかの関連する機構も扱います。

## なぜ処理系開発者が知っておくべきか

「自分の言語はメモリ安全だから関係ない」と思うかもしれません。しかし現実の処理系では、GCやスケジューラ、例外処理といったランタイムがCやアセンブリで書かれていることが多く、FFIでCのライブラリも呼びます。言語が安全でも、プロセスの中に不安全なコードがあれば攻撃の足がかりになります。

さらに処理系開発者は、hardeningと3つの立場で関わります。

1. 利用者として：ランタイムやFFI先のCコードをhardeningで守ります。
2. 提供者として：コード生成器が、hardening機構に対応した機械語とオブジェクトファイルを出力します。たとえばIntel CETのIBTが有効なプロセスでは、間接分岐の飛び先にすべて`ENDBR64`命令が必要です。
3. 破壊者として：スタックをコピーする継続、リターンアドレスの書き換え、ポインタの上位ビットを使ったタグ付け、JITといった処理系の定番テクニックは、hardening機構とぶつかります。

**3つ目の立場は見落とされがちですが、処理系開発者に特有の問題です**。この資料では、この3つの立場それぞれで何に気を付ければよいかがわかることを目指します。

## この資料の読み方

最初の2章で、何から何を守るのかと、昔からある基本的な緩和策を整理します。続くサニタイザからMTEまでの各章では、機構ごとにしくみと有効にする方法を説明し、コード生成器とランタイムの注意点を挙げます。

「ランタイムとFFIで気を付けること」の章では、機構ごとの話を「スタック切り替え」「非局所脱出」「GC」「JIT」といった場面ごとにまとめ直しています。自分の処理系に関係する場面から読むのもよいでしょう。最後のチェックリストは、実装やレビューのときに見返すためのものです。

## 前提と表記

x86-64とAArch64のアセンブリが少し読めることを前提にします。不安があれば、『Binary Hacks Rebooted』のHack #2（アセンブリ入門）とHack #83（ABIと呼び出し規約）が役に立ちます。主にLinux（ELF）を想定し、必要に応じてmacOS／iOS、Windows、Androidに触れます。

コマンドの例はGCC 13、Clang 21、GNU binutils 2.42程度を想定しています。OSやツールの対応バージョンは執筆時点（2026年）の情報です。この分野は変化が速いので、実際に使うときは参考文献の一次資料で確認してください。
